# 技术方案对比与选型结论

## 1. 方法

采用**加权评分法**：先定义 9 个评价维度与权重，再对 8 个候选方案按 1–5 分评分（5 最优），最后计算加权总分并做敏感性分析。评分依据来自 `03-research-landscape.md` 的事实调研，不凭印象加分。

### 1.1 评价维度与权重

| 维度 | 权重 | 定义 | 为什么重要 |
|---|---|---|---|
| 内容/多领域建模 | 15 | 类型安全的内容集合、分类/标签/筛选、案例研究结构 | 本站核心是 7 个领域的项目展示 |
| 性能 | 15 | 默认输出体积、图片/字体优化、CWV 可达性 | 个人站的第一印象与移动端体验 |
| 设计上限 | 15 | 布局与动效自由度、组件化能力、设计系统可落地性 | 明确要求"美观度" |
| 生态与长期维护 | 15 | 版本活跃度、集成数量、社区规模、升级风险 | 长期目标，不能一年后无法升级 |
| 开发体验/DX | 10 | 类型安全、热更新、调试、测试集成 | 单人长期维护的效率 |
| SEO/可访问性 | 10 | 元数据、结构化数据、语义化、a11y 工具链 | 作品集需要被检索、被所有人访问 |
| 部署与运维 | 10 | 托管成本、是否需要服务端、回滚难度 | 零运维是硬约束 |
| 开源与协作 | 5 | 许可证、贡献流程、可复用性 | 项目要求可开源 |
| 学习成本 | 5 | 上手时间、概念负担 | 单人项目，但权重不宜过高 |

### 1.2 评分标准

| 分值 | 含义 |
|---|---|
| 5 | 该维度最优，无需额外工程即可满足需求 |
| 4 | 优秀，少量定制即可 |
| 3 | 可用，需要明显额外工作 |
| 2 | 勉强，存在结构性障碍 |
| 1 | 不满足 |

### 2.1 复算示例（Astro 7）

```
5×15 + 5×15 + 5×15 + 5×15 + 4×10 + 5×10 + 5×10 + 5×5 + 4×5
= 75 + 75 + 75 + 75 + 40 + 50 + 50 + 25 + 20
= 485
加权总分 = 485 / 100 = 4.85
```

| 方案 | 主要扣分点 |

| SaaS | 内容 2：结构化能力受限；开源 1：不可开源；SEO 3：可控性差 |

## 3. 敏感性分析

结论是否依赖权重选择？测试三种明显不同的权重场景：

| 场景 | 权重侧重 | Astro | Nuxt | Next | 结论 |
|---|---|---|---|---|---|
| A（基线） | 四项各 15，均衡 | 4.85 | 4.45 | 4.40 | Astro 第一 |
| B（内容优先） | 内容 25、性能 10、设计 10、生态 15、其余同基线 | 4.85 | 4.50 | 4.35 | Astro 第一 |
| C（上手优先） | 学习 40、DX 30、内容/性能/设计/生态各 10 | 4.50 | 4.30 | 3.90 | Astro 第一 |

**原因**：Astro 在内容、性能、设计、生态、SEO、部署、开源 7 个维度均为 5 分，只有 DX 与学习成本为 4 分。只要权重不极端集中到"学习成本"单项，其领先不会被翻转。唯一需要警惕的是团队完全不具备 JS/TS 经验——本项目不适用。

## 4. 总拥有成本（TCO）对比

> 数字为**量级估算**（2026-10 公开定价 + 经验值），用于方案间相对比较，不作为报价。

| 方案 | 托管成本/月 | 运维/月 | 年度升级工作量 | 主要隐性成本 |
|---|---|---|---|---|
| Astro + GitHub Pages | $0 | ≈0 | 2–4h | 生态迁移（Sätteri）跟踪 |
| Next + Vercel | $0（Hobby，非商业）或 $20 | ≈0 | 4–8h | 平台条款、RSC 升级、构建分钟数 |
| Nuxt + 静态托管 | $0 | ≈0 | 3–6h | 生态规模较小，问题检索成本高 |
| SvelteKit + 静态托管 | $0 | ≈0 | 3–6h | 内容层自建 |
| Hugo + 静态托管 | $0 | ≈0 | 1–3h | 设计/交互定制人力成本高 |
| 模板改造 | $0 | ≈0 | 不确定 | 停更后自行维护；许可证风险 |
| 自建 CMS（Payload/Strapi） | $5–20（VPS/DB） | 4–8h | 8–16h | 备份、安全补丁、数据库迁移 |
| SaaS 建站 | $8–20 | ≈0 | 0 | 迁移锁定、导出受限 |

结论：静态方案在成本维度几乎无差异，**差异在长期设计与内容演进能力**，这正是 Astro 的优势区。

## 5. 选型结论

### 5.1 采纳

| 层 | 选择 | 理由 | ADR |
|---|---|---|---|
| 框架 | Astro 7（SSG） | 内容建模 + 零 JS 默认 + 静态部署 | 0001 |
| 语言 | TypeScript 6.0.3 | `@astrojs/check` 与 typescript-eslint 双重约束 | 0011 |
| 样式 | Tailwind CSS 4 + OKLCH 令牌 | CSS-first、与 Vite 8 兼容、设计上限高 | 0002 |
| 内容 | Content Collections + Zod + MDX | 构建期类型安全与字段级报错 | 0003 |
| 交互 | 原生 TS island + View Transitions | 控制 JS 预算，避免框架税 | 0004 |
| 搜索 | Pagefind + astro-pagefind | 零服务、构建期索引 | 0005 |
| 部署 | GitHub Pages 主 + Cloudflare Pages 备 | 免费、静态、可回滚 | 0007 |
| 测试 | Vitest + Playwright + axe + LHCI | 覆盖单元到体验 | 0008 |
| 许可 | MIT | 最大化复用与贡献 | 0010 |

### 5.2 明确不采纳

- 运行时后端与数据库（Payload/Strapi/Directus）：无需求，违反零运维目标。
- 评论系统、账号体系：维护成本 > 收益。
- 非宽松许可证模板：合规风险。
- 重型 3D/WebGL：性能与可维护性代价。
- 服务端搜索（Meilisearch/Algolia）：引入服务依赖。

### 5.3 触发重新评估的条件

1. 需要多人协作在线编辑 → 先评估 Sveltia CMS，再评估 Payload。
2. `@astrojs/check` 支持 TS 7 → 按 ADR 0011 的升级流程处理。
3. Astro 7 出现无法绕过的阻塞缺陷 → 回退 Astro 6（保留 `unified()` 管线与相同内容模型）。
4. 需要英文正文 → 启用预留的 i18n 路由，不换框架。

## 6. 与需求的对应

| 需求 | 选型如何满足 |
|---|---|
| 多领域项目展示（FR-02） | Content Collections 的 `domain` 枚举 + `tags` + `getProjectFacets()` |
| 美观度（01 §3） | Tailwind 4 + 自建设计系统 + CSS 新特性 + View Transitions |
| 性能（NFR-01/02） | Astro 默认零 JS + `astro:assets` + 字体预算 |
| 可开源（01 §4） | 无专有依赖、MIT、纯静态产物 |
| 长期维护（NFR-10） | 内容与代码分离、类型检查、文档与 ADR 同步 |
